# Deploying GhostWalk

Two halves: the **backend** (HydraDB + MinIO + API + Caddy HTTPS) on a Linux VM, and the **frontend** (the Vite app) on Vercel.

Live: frontend https://ghostwalk-henna.vercel.app, API https://api.13-51-194-36.sslip.io (status: `/api/health`).

## 1. Backend on a Linux VM (>= 4 GB RAM)

```bash
git clone https://github.com/redcode333/GhostWalk && cd GhostWalk
FRONTEND_ORIGIN=https://<your-project>.vercel.app ./deploy/setup.sh
```

`deploy/setup.sh` installs Docker if it is missing, writes `deploy/.env` (random HydraDB and admin tokens; `API_DOMAIN` defaults to `api.<vm-ip>.sslip.io`, or set `API_DOMAIN=api.example.com`),
starts `deploy/docker-compose.prod.yml` and runs `deploy/smoke.py` against it. Open ports 80 and 443.

| service | what it is |
|---|---|
| `hydradb` | the pinned HydraDB 0.4.0 image, no published ports; its graph is stored in MinIO, the `hydradb-data` volume is only a cache; not restarted automatically |
| `minio` | S3-compatible object storage, internal network only (no published ports, no console), data in the `minio-data` volume; built from source by `deploy/minio/Dockerfile` |
| `minio-init` | one-shot: creates the bucket and a user that can only use it |
| `api` | GhostWalk with `GW_STORE=hydradb`, `AUTH_MODE=none`, `GW_PUBLIC_DEMO=1`, rate limit on `/v1/*` and on POSTs, CORS for the frontend origin only |
| `caddy` | HTTPS (Let's Encrypt) in front of the API; certificate data in the `caddy-data` volume |

`STORAGE=minio` is the default; `STORAGE=local ./deploy/setup.sh` keeps HydraDB's data on the local volume instead (same behaviour, measured below).

**The public demo** is a sandbox: anyone can trigger a demo outage, read verdicts, apply a postmortem and ask `why-edge`; settings, onboarding and webhooks answer 403. It is rebuilt every night at
03:00 UTC (or `POST /api/demo/reset` with the `X-GW-Admin` token). `GET /api/health` is the status endpoint.

Update later: `./deploy/setup.sh update` (the `deploy` workflow does this over SSH on every push to `main` that touches the backend; secrets `VM_HOST`, `VM_USER`, `VM_SSH_KEY`).

## 2. Frontend on Vercel

```bash
cd web
vercel link                                   # once
vercel env add VITE_API_URL production        # https://<API_DOMAIN>
vercel --prod
```

`web/vercel.json` sets the Vite build and the single-page-app rewrite (every path serves `index.html`, so `/demo` works). Put the resulting `https://<project>.vercel.app` into `GW_CORS_ORIGINS`
on the VM (`deploy/.env`, then `./deploy/setup.sh update`) so the browser may call the API.

## 3. Smoke test

```bash
python deploy/smoke.py --api https://<API_DOMAIN> --frontend https://<project>.vercel.app --rate-limit-check
```

Checks the landing page and that its bundle points at the API, `/demo`, health, that the store is HydraDB, CORS (allowed for the frontend, refused for others), the proof data, a demo outage verdict,
learn -> apply (answers at once with `saving`, the revision moves when the write lands), `why-edge` on a learned edge, the sandbox guard and the rate limit.

## Object storage (MinIO)

HydraDB stores GhostWalk's graph on S3-compatible object storage (MinIO). Delete HydraDB's local data and the graph comes back from object storage.

Configuration (from HydraDB's Helm chart): `CLOUD_PROVIDER=aws`, `AWS_ENDPOINT=http://minio:9000`, `AWS_BUCKET_NAME`, `AWS_DEFAULT_REGION`, `AWS_ALLOW_HTTP=true` (MinIO is only reachable inside the compose network), and a bucket-scoped
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` generated by `setup.sh` into `deploy/.env` (never committed or printed). HydraDB's writer leases and manifest pointer need conditional writes; its startup log confirms
"object store passed the create-only probe: writers allowed" on MinIO `RELEASE.2025-09-07T16-13-09Z`. MinIO no longer publishes container images, so `deploy/minio/Dockerfile` builds that release from source.

Checked on the VM (Xeon 8488C, 2 vCPU, 7.6 GB): `deploy/smoke.py` passes; `deploy/parity_check.py` (60 incidents with learning, the demo company) gives identical rankings and an identical learned graph against the in-memory learner;
`make durability-demo` (stop everything, delete only HydraDB's local volume, keep MinIO's, start again) returns an identical ranking and `why-edge` (`docs/measurements/durability_demo_vm.txt`); and a learn after restarting HydraDB is accepted.

| warm latency on the VM (generated companies, learning on) | MinIO | local disk |
|---|---|---|
| verdict p50 / p95 | 1.2 / 1.9 ms | 1.3 / 1.8 ms |
| cached verdict p50 | 0.83 ms | 0.86 ms |
| one HydraDB 1-hop query p50 | 3.0 ms | 2.9 ms |
| learning write p50 / p95 (the HydraDB commits behind one Apply) | 561 / 1,379 ms | 550 / 1,380 ms |

Object storage costs nothing measurable here: the write time is HydraDB's own commit work. Raw numbers: `results.json` `ops.vm.minio` and `ops.vm.local`.

### The restart bug (fixed) and why HydraDB is not restarted automatically
HydraDB 0.4.0 rejected every HTTP write after a restart with `409 mutation_conflict: idempotency identity was reused for a different request`. Cause, from its source: HTTP requests without a `query_id` are numbered
`http-query-1, 2, ...` by a counter that starts at 1 in every process, and writes are deduplicated durably by that number, so after a restart the new process reuses numbers that old receipts already hold for other statements.
GhostWalk now sends its own unique `query_id` with every request (the same one when it re-sends a request, so retries stay idempotent); `tests/test_hydra_restart.py` fails without it. Details and a curl reproduction to file
upstream: [hydradb-issue.md](hydradb-issue.md). `hydradb` keeps `restart: "no"` in the prod compose anyway, and the API logs a loud error line if HydraDB ever rejects writes.
